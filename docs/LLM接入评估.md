# 大模型接入评估（逐环节）

> 结论先行：**P1–P7 每个环节都有必须用大模型的位置，但也有"不该用"的位置。**
> 判定标准只有一条：**这一步的产出是否需要"理解自然语言 / 生成自然语言"**。
> 纯结构化比对（对齐、计分、ID 生成、去重）用规则更稳、更可解释，硬塞模型反而是负分。
>
> 现状：`backend/tools/llm_client.py` 已实现真实调用（OpenAI 兼容协议，非本地伪装），
> 并已接入 **P5 澄清推断**（缺失字段的定义/单位/类型补写，带置信度与依据，可逐项驳回）。
> 其余环节的接入点在下表逐项列出，按 P0 优先级推进。

---

## 0. 接入层设计（已落地）

| 项 | 内容 |
|---|---|
| 协议 | `POST {base_url}/chat/completions`，Bearer 鉴权，JSON mode（`response_format`） |
| 配置 | 环境变量 `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`，或 `data/llm_config.json`；`LLM_ENABLED=0` 可强制关闭 |
| 降级 | 未配置时 `available()=False`，调用方走规则兜底，界面显示「未配置（走规则兜底）」，**不伪装成调过模型** |
| 审计 | 每次调用写 `deliverables/llm/trace.jsonl`：`model / prompt_hash / elapsed_ms / usage / ok`，评委可查"哪一步真用了模型" |
| 防泄漏 | 只发字段名、类型、已有约束等结构化文本，**不发原始文档全文**；超长截断并在 trace 标注 |
| 自检 | `GET /api/llm/status`、`POST /api/llm/selftest`；P5 顶部有「模型连通性自检」按钮 |

## 1. 逐环节评估

### P0 · 数据接入与就绪校验

| 候选任务 | 是否值得 | 说明 |
|---|---|---|
| 判断上传文件"能不能用" | ❌ 不该用 | 文本层字符数、三表表头、列名匹配都是确定性的，用模型反而不可解释、还会偶发误判 |
| **识别"这份表是哪一类"（D1 文档 / D2 需求表 / D3 预期输出）** | ✅ 值得 | 用户随手传的表头命名五花八门（"属性中文名称" vs "字段名" vs "中文名"），规则白名单永远补不全。用模型做**表头语义归类**，返回 `{kind, mapping:{原列名→标准列名}, confidence}`，作为规则匹配的补充（规则命中优先，未命中才问模型） |
| 生成《数据准备清单》说明文案 | ⚪ 可选 | 模板足够，模型只会增加不确定性 |

**优先级：P2（有价值但不紧急）**

---

### P1 · 文档解析工作台

| 候选任务 | 是否值得 | 说明 |
|---|---|---|
| PDF/Word 转文本、表格抽取 | ❌ 不该用 | 这是 `pdfplumber` / `python-docx` 的活；模型做这个既慢又不可复现 |
| **扫描件无文本层时的兜底（OCR 后的版面理解）** | ✅ 值得 | 当前 A 组两份 PDF 文本层 0 字符，规则直接判 degraded。接入视觉模型/OCR 后，让模型判断"这页是目录/表格/正文""表格的列是什么"，比纯规则强得多 |
| **章节树构建** | ✅ 值得 | 现在章节粒度退化为"文档级"。让模型读目录页/标题层级，输出 `{level, title, page_range}`，P4 的矩阵行维度立刻有意义 |
| 解析质量评级（ok/degraded） | ❌ 不该用 | 字符数阈值即可，模型评级不可审计 |

**优先级：P1（直接决定 A 模式能不能评）**

---

### P2 · 知识抽取审核台

| 候选任务 | 是否值得 | 说明 |
|---|---|---|
| **候选对象类/属性抽取（核心）** | ✅✅ 必须 | 现在扫描件场景是"文件名主题 + 底座弱匹配"生成的候选，全部低置信、本质上不是抽取。正确做法：分块喂给模型，要求返回 `{object_classes:[{name, evidence_span}], attributes:[{class, name, unit, data_type_hint, evidence_span}]}`，**必须给原文片段作为证据**，无证据的候选一律不入库 |
| **术语归一（同义词 → 规范名）** | ✅ 值得 | 现在靠 D6 词表 240 组做精确替换，表外词一律不归一。模型可处理"Ø" "φ" "直径" "DN" 这类变体，并给出 `canonical + confidence + 依据` |
| 置信度打分 | ⚠️ 谨慎 | 模型自评分不可信，易被刷。置信度应由**证据强度**推导（有原文片段=高、仅主题匹配=低），模型分数只作参考并标注 |
| 候选去重合并 | ❌ 不该用 | 归一化后字符串比对更稳 |

**优先级：P0（这是"知识抽取"环节的门面，现在最像规则引擎）**

**✅ 已接入（2026-10-22 深夜）**：`knowledge_extractor._llm_enrich_a()`

| 做了什么 | 实测 |
|---|---|
| 术语归一（D6 词表未命中的写法）→ `term_norm = {method: "llm", reason}` | 22 条 |
| 候选定义补写（原先是「（参考库命中）」占位）→ 标 `llm_definition` | 12 条，界面加「AI 定义」标 |
| 正文抽取（带 `evidence_span`，无证据不采纳） | **跳过**：内置 A 文档是无文本层扫描件，`llm.skipped_extract` 已如实标注；上传可解析文档后自动启用 |
| 三项任务**并发**（串行 231s → 并发 69–97s） | 首次 ~97s，之后走缓存秒回 |

### P3 · 双知识底座

| 候选任务 | 是否值得 | 说明 |
|---|---|---|
| 建图、写 OWL、算指标 | ❌ 不该用 | 确定性工程活，模型只会引入不可复现 |
| **父子类判定（subClassOf 对齐）** | ✅ 值得 | 现在 157 个对象类的父类不在子集内，`subClassOf` 全为 0。让模型判断"A 是否 B 的子类"，输出 `{parent, child, confidence, reason}`，人工确认后入图 |
| **同义类合并（跨表同名不同写法）** | ✅ 值得 | 如"管道" vs "管道（管段）"。模型给合并建议 + 保留哪个名的理由 |
| 语义查询（P3 的"推理查询"框） | ✅ 值得 | 把自然语言问题转成图查询（类/属性/关系三元组），回答时引用命中的节点 id，可溯源 |

**优先级：P1**

### P4 · 发现式梳理（模式 A）

| 候选任务 | 是否值得 | 说明 |
|---|---|---|
| **候选标准的新颖性判断** | ✅ 值得 | 现在是"和模拟库做字符串相似度"，只能判"像不像"。模型能判"业务上是不是同一件事"，输出 `{verdict: 可复用/需合并/确为新增, reason, 引用哪条已有标准}` |
| **立项优先级/价值评估** | ✅ 值得 | 输入候选 + 覆盖盲区 + 业务域，输出"先做哪几个类、为什么"，对应评委关心的"梳理策略" |
| **覆盖盲区的业务解读** | ✅ 值得 | 规则只能报"哪些域没覆盖"，模型能说"这意味着通风专业的管件标准缺失，会影响采购对接" |
| 密度矩阵计算 | ❌ 不该用 | 纯统计 |

**优先级：P2**（演示讲得好，但不影响硬指标）

**✅ 已接入（2026-10-22 深夜）**：`landscape_analyst._llm_enrich_p4()`

| 做了什么 | 实测 |
|---|---|
| 新颖性判断：每条给 `可复用 / 需合并 / 确为新增` + 命中的现有条目 + 理由 | 8 条 |
| 立项优先级：`priority 1–5` + `score` + 理由（结合覆盖盲区） | 8 条 |
| 两个任务**并行**发出，只判前 8 条（15 条 + 200 条现有条目实测要 5 分钟） | 首次 ~40s |
| 模型结论与规则结论**并存**，界面标「与规则不一致」，不静默覆盖 | 已验证 |

样例（真实返回）：
> 「物项」→ 确为新增 · 优先级 1 ·「现有条目均为具体设备或材料类别，未覆盖作为总对象类的"物项"概念。」
> 「管件」→ 确为新增（对照 60 条现有条目）·「现有条目仅有三通、弯头、法兰等具体连接部件，未覆盖"管件"这一上位对象类。」

### P5 · 需求转化（模式 B）—— **已接入**

| 候选任务 | 是否值得 | 现状 |
|---|---|---|
| **缺失字段的定义/单位/类型补写** | ✅✅ 必须 | **已实现**：`llm.suggest_definitions()`，一次最多 12 个字段，返回 `definition / unit / data_type / confidence / reason`，写入 `inferences[].llm_*`，`basis` 注明"由大模型 X 补写"；低于 0.6 标"仅作参考" |
| **澄清问题生成（把"缺什么"变成"问什么"）** | ✅ 值得 | 现在是模板句"「X」的口径应如何确定？"。模型可生成业务人员看得懂的问题，并给 2–3 个可选项 |
| **冲突消解建议** | ✅ 值得 | 同一属性在不同类下口径不同（如长度 50 vs 256），模型给"取哪个、为什么、影响谁" |
| 类型自然语言 → 技术类型转换 | ❌ 不该用 | `字符型(50) → String/VARCHAR(50)` 是硬规则，模型会偶发幻觉写错长度 |
| 完备性计分 | ❌ 不该用 | 权重公式必须可审计 |

**优先级：P0（已完成接入，待配 key 验证真实输出质量）**

### P6 · 标准生成与演化

| 候选任务 | 是否值得 | 说明 |
|---|---|---|
| **属性定义（definition）生成** | ✅✅ 必须 | 需求表里定义填写率 **0%**（855 条全空）。这是最该用模型的地方：按"对象类 + 属性名 + 格式"生成一句话定义 |
| **命名规范化** | ✅ 值得 | 统一成"中文名 + 英文名 + 命名风格"，模型判断"壁厚"该叫 `WallThickness` 还是 `NominalThickness` |
| **演化匹配的语义判断** | ✅ 值得 | 现在字符串相似度 ≥0.85 判"需合并"，容易把"外径"和"外径（mm）"分开、把"长度"和"宽度"误合。模型给语义等价判断 |
| ID 生成（大类缩写 + 6 位 / Attr+6 位） | ❌ 不该用 | 规则生成，必须可复现且唯一 |
| 质量分/可使用率 | ❌ 不该用 | 公式必须固定 |

**优先级：P0（定义生成直接决定"标准可用率"这个硬指标）**

### P7 · 准确率评测

| 候选任务 | 是否值得 | 说明 |
|---|---|---|
| **错因归类（为什么这条判错）** | ✅ 值得 | 现在是固定 8 类枚举。模型能给出"这条不是漏抽，是输出侧把一条拆成主/支两条"这种**具体解释**，评委最爱看 |
| **partial 的语义等价判断** | ⚠️ 谨慎 | "壁厚" vs "公称壁厚" 算不算一致？模型可给建议，但**必须人工确认**，且不能进入 official 指标（否则准确率不可复现）。建议单列"AI 复核建议"，不改主分 |
| 对齐、计分、F1 | ❌ 绝对不能 | 评测的核心价值是"可复现、可审计"。模型参与计分 = 每次跑分不一样 = 直接出局 |

**优先级：P2（只做解释，不碰分数）**

## 2. 建议的推进顺序

| 阶段 | 内容 | 预期效果 |
|---|---|---|
| **第 1 步（已完成）** | `llm_client` + P5 定义补写 + 状态/自检接口 | 证明"真调模型"，且断网可降级 |
| **第 2 步（已实现，待余额）** | P6 定义生成（`/api/standard/enrich`，15 条/批、单次上限 60） | 规范性维度上升（用 stub 实测：30 条补全后 normativity 3.4 → 5.6）；导出表格不再"定义空白" |
| **第 3 步** | P2 候选抽取（带证据片段）+ 术语归一 | 把"假抽取"换成"真抽取"，A 模式才有说服力 |
| **第 4 步** | P4 新颖性/优先级、P3 父子类对齐 | 讲"梳理策略"，不只讲"生成表格" |
| **第 5 步** | P7 错因解释（不碰分数） | 报告可读性 |

## 3. 必须守住的三条红线

1. **分数不许模型参与**：P7 的对齐、判定、计分全部走确定性代码。模型只写解释。
2. **无证据不入库**：P2/P3 由模型产出的候选/关系，必须附原文片段或已有标准 id，否则只进"待确认"，不进图谱。
3. **可降级**：任何模型调用失败都必须回落到规则路径，并在界面标注"本次未使用模型/使用了模型 X"，不允许静默。

**踩过的坑（留给后来人）**

1. `key: sk-xxx` 这种带前缀的写法，加载器会用正则抽出 `sk-` 那一段；纯 key 直接粘也行。
2. 记事本写 JSON 会带 BOM，加载统一用 `utf-8-sig`，否则解析失败会被静默吞掉。
3. 百炼的模型名是小写 `qwen3.8-max`（不是 `Qwen3.8-Max`），写错会 400 再走回退。
4. 进程重启后内存里的 `_STANDARDS` 会空 —— `list_standards()` / `get_standard()` 已改为回落读磁盘。
